# Requirements Document

## Project Description (Input)

開発者(えちょ)は、記事の置き場 `site/src/content/posts/` を整理したい。今は 424 本の記事が平らに並び、そのうち 399 本は 2003〜2010 年の、もう増えない古い記事である。新しい記事を書くたびに、エディタのファイル一覧で古い記事の山をかき分けることになる。

今の仕組みは、記事をサブフォルダに置くとビルドを止める(記事の URL を決める仕組みが、識別子に `/` があると拒む)。公開後の確かめ(`npm run verify`)も、サブフォルダの非公開の記事の公開パスを決められない。steering の `structure.md` にも「サブフォルダに置かない」とある。

変えたいこと: `posts/` の下なら、どのフォルダに記事を置いてもよいようにする。URL はファイル名だけで決まり、フォルダ名は URL に入らない。同じファイル名の記事が 2 本あれば、両方を挙げてビルドを止める。そのうえで、2010 年までの記事を `posts/archive/` へ移す。移す前と後で、公開パスは 1 つも変えない。

詳しい背景と、選ばなかった案は、同じフォルダの `brief.md` にある。

## Introduction

この spec は、記事の置き場にフォルダを使えるようにし、古い記事をフォルダへ移す。読者から見える変化は無い。変わるのは、開発者が原稿を置く場所だけである。

完了済みの spec `site-astro-redesign` は「記事はサブフォルダに分けず、1 つの置き場に平らに置く」と決めた(その Requirement 2 の 17)。この spec は、その決まりを改める。記事の URL の決まり(`/YYYY/MM/DD/<名前>.html`。日付と名前はファイル名から)は、そのまま保つ。

### この要件の決まり方

`brief.md` と、開発者の判断(2026-10-28)をもとに確定した。

- `posts/` の下なら、どのフォルダに置いてもよい。`archive/` だけに限らない。URL はファイル名だけで決まる(Requirement 1)。
- フォルダが違っても、同じファイル名の記事があれば、両方のファイルを挙げてビルドを止める(Requirement 2)。
- 2010 年までの記事を、この spec の中で `posts/archive/` へ移す。移す前と後で、ビルドが出す公開パスの一覧を変えない(Requirement 4・5)。

### この文書で使う言葉

- **記事の置き場**: `site/src/content/posts/`。
- **直下**: 記事の置き場そのもの(フォルダの中ではない所)。
- **フォルダ**: 記事の置き場の下にあるフォルダ。深さは問わない(`archive/`、`archive/old/` など)。
- **ファイル名**: 記事のファイルの名前(`YYYY-MM-DD-<名前>.md`)。フォルダの部分を含まない。
- **ファイルの場所**: 記事の置き場からの、フォルダを含むパス(`archive/2004-05-01-foo.md` など)。
- **古い記事**: ファイル名の年が 2010 年以前の記事。
- **公開サイト**: `https://ekicyou.github.io/` で読者に見えるもの。ビルドの成果物と同じ。
- **ビルド**: 原稿からサイトを作る処理(`npm run build`。公開パイプラインの中でも同じ)。
- **公開後の確かめ**: ビルドの成果物を検査する処理(`npm run verify`)。
- **移動作業**: この spec の作業として行う、古い記事を `archive/` へ移し、前後を突き合わせる一連の作業。
- **プロジェクト文書**: steering(`.kiro/steering/`)と `CLAUDE.md`・`README.md`。

## Boundary Context

- **In scope**:
  - 記事の置き場の下のフォルダに置いた記事を、直下の記事と同じに受け入れること
  - 同じファイル名の記事が重複したときに、ビルドを止めること
  - 公開後の確かめを、フォルダに置いた記事に合わせること
  - これらを確かめるテストの更新
  - 古い記事の `archive/` への移動と、前後の公開パスの突き合わせ
  - プロジェクト文書のうち、記事の置き場に触れる箇所の更新
- **Out of scope**:
  - 記事の URL の変更
  - 記事の内容(本文と front matter)の書き換え
  - フォルダ名を、記事のページ・一覧・フィードに出すこと
  - 記事のページ・一覧・フィードの見た目
  - 文書(`site/src/content/doc/`)の置き場と URL の決まり。文書は今までどおり、フォルダ(題材)が URL に入る(`/doc/<題材>/<名前>.html`)。記事とは決まりが違うまま残す。
  - 画像(`site/public/`)の置き場
  - 2011 年以降の記事の整理
- **Adjacent expectations**:
  - 記事のファイル名の決まり(`YYYY-MM-DD-<名前>.md`、名前に `index` は使えない)、front matter の項目、`published: false` の扱いは、`site-astro-redesign` が決めたまま変わらない。フォルダに置いた記事にも、同じ決まりが掛かる。
  - これから書く記事は、直下に置く。年が進んで、さらに古い記事を `archive/` へ移すのは、開発者の手作業でよい。そのとき仕組みの変更は要らない(Requirement 1 の 3)。
  - 開発者は今までどおり `master` へ直接 push して記事を公開してよい。

## Requirements

### Requirement 1: フォルダに置いた記事を公開する

**Objective:** As a 開発者, I want 記事の置き場の下のどのフォルダにも記事を置けること, so that 古い記事を片付けて、新しい記事を書くときにファイル一覧で迷わずに済む

#### Acceptance Criteria

1. The ビルド shall 記事の置き場の下のフォルダ(深さを問わない)に置いた記事を、直下に置いた記事と同じ決まりで受け入れ、ビルドを止めない。
2. The 公開サイト shall フォルダに置いた記事を、ファイル名の日付と名前だけから決まる URL(`/YYYY/MM/DD/<名前>.html`)で公開し、フォルダ名を URL に入れない。
3. When 開発者が、ファイル名を変えずに、記事を直下とフォルダの間、またはフォルダ同士の間で移したとき, the 公開サイト shall その記事を、移す前と同じ URL で公開する。
4. The 公開サイト shall フォルダに置いた記事を、直下の記事と区別せずに、記事の一覧・フィード・前後の記事に載せ、ファイル名の日付と名前で決まる今までと同じ順に並べる。
5. The 公開サイト shall フォルダ名を、記事のページ・一覧・フィードのどこにも出さない。
6. Where フォルダに置いた記事が `published: false` を指定している, the 公開サイト shall その記事を、ページ・記事の一覧・フィードのどこにも出さない。
7. If フォルダに置いた記事のファイル名が決まりに合わないとき(非公開の記事を含む), the ビルド shall 止まり、フォルダを含むファイルの場所と理由を示す。

### Requirement 2: 同じファイル名の記事を止める

**Objective:** As a 開発者, I want 同じファイル名の記事が 2 本あるときにビルドが止まること, so that 同じ URL の記事が知らないうちに片方だけ公開される事故を防げる

#### Acceptance Criteria

1. If 記事の置き場の下に、ファイルの場所が違い、ファイル名が同じ記事が 2 本以上あるとき, the ビルド shall 止まる。ファイル名が同じとは、大文字・小文字を区別せずに比べて綴りが一致することをいう(`Foo.md` と `foo.md` も同じとみなす。Windows の手元のビルドで、成果物の片方が黙って上書きされるのを防ぐため)。
2. When ビルドが同じファイル名の記事で止まるとき, the ビルド shall 重複している記事すべてのファイルの場所を示す。
3. The ビルド shall 非公開の記事も重複に数える。公開の記事と非公開の記事、非公開の記事同士の重複でも止まる。
4. While 記事の置き場の下に同じファイル名の記事が無い, the ビルド shall 記事の置き方(直下かフォルダか、どのフォルダか)を理由に止まらない。

### Requirement 3: 確かめの仕組みを合わせる

**Objective:** As a 開発者, I want 公開後の確かめとテストが、フォルダに置いた記事でも働くこと, so that マージの前の確かめ(`npm test`・`npm run verify`)を、今までどおり信じられる

#### Acceptance Criteria

1. The 公開後の確かめ shall フォルダに置いた非公開の記事についても、その公開パスが成果物に無いことを確かめる。
2. The 公開後の確かめ shall 記事がフォルダに置かれていることを理由に、誤りも警告も出さない。
3. If 非公開の記事の公開パスをファイル名から決められないとき, the 公開後の確かめ shall 誤りとし、フォルダを含むファイルの場所を示す。
4. The テスト(`npm test`) shall フォルダに置いた記事の公開パスが、ファイル名だけで決まり、フォルダ名を含まないことを確かめる。
5. The テスト(`npm test`) shall 同じファイル名の記事が重複したときに、重複している記事すべてのファイルの場所を示して止まることを確かめる。
6. The テスト(`npm test`) shall 「サブフォルダの記事を拒む」ことを確かめるテストを残さない。

### Requirement 4: 古い記事を `archive/` へ移す

**Objective:** As a 開発者, I want 2010 年までの記事が `posts/archive/` にまとまっていること, so that 直下には、これから増える新しい記事だけが並ぶ

#### Acceptance Criteria

1. The 移動作業 shall 古い記事(ファイル名の年が 2010 年以前の記事)を、非公開の記事を含めて、すべて `site/src/content/posts/archive/` へ移す。
2. The 移動作業 shall 移す記事のファイル名と中身(front matter と本文、改行)を変えない。
3. The 移動作業 shall 移した記事を、移動として履歴を辿れる形で移す(移した記事の履歴が、移す前から続いて見える)。
4. When 移動作業を終えたとき, the 記事の置き場 shall 直下に 2011 年以降の記事だけを持ち、`archive/` に 2010 年以前の記事だけを持つ。
5. The 移動作業 shall 2011 年以降の記事を移さず、書き換えない。
6. The 移動作業 shall 記事の移動を、PR のブランチの上で、仕組みの変更とは別のコミットにする(同じ PR に入れる)。PR は squash マージされるので、`master` では 1 つのコミットになってよい(`workflow.md`)。

### Requirement 5: 公開済みの URL を保つ

**Objective:** As a 読者, I want 記事の置き場が整理されても、公開済みのページが同じ URL で届くこと, so that 古いリンクやブックマークが切れない

#### Acceptance Criteria

1. The 公開サイト shall 移動作業の前と後で、ビルドが出す公開パスの一覧を変えない(1 つも増えず、1 つも減らない)。
2. The 公開サイト shall 保つパスの一覧(`site/tests/kept-paths.txt`)にあるパスを、移動作業の後も公開する。
3. The 公開サイト shall 移動作業の前と後で、記事の一覧・フィード・前後の記事に載る記事と、その並びを変えない。
4. Where 移した記事が `published: false` を指定している, the 公開サイト shall 移動作業の後も、その記事をどこにも出さない。
5. When 移動作業を終えたとき, the 移動作業 shall 前と後のビルドの公開パスの一覧を突き合わせた結果と、公開後の確かめ(`npm run verify`)の結果を、開発者に示す。
6. If 突き合わせで、公開パスの増減が 1 つでも見つかったとき, the 移動作業 shall 完了とせず、増えたパスと減ったパスを開発者に示す。

### Requirement 6: プロジェクト文書を合わせる

**Objective:** As a 開発者, I want プロジェクト文書が新しい記事の置き方を正しく書いていること, so that 後で記事を書くときや、AI に記事を任せるときに、古い決まりに従ってしまわない

#### Acceptance Criteria

1. The プロジェクト文書 shall 記事を記事の置き場の下のどのフォルダにも置けること、URL はファイル名だけで決まりフォルダ名は入らないこと、を記す。
2. The プロジェクト文書 shall 同じファイル名の記事があるとビルドが止まること(フォルダが違っても、非公開の記事でも、大文字・小文字だけが違っても)を記す。
3. The プロジェクト文書 shall 古い記事が `archive/` にあること、これから書く記事は直下に置くこと、さらに古い記事を `archive/` へ移すのは手作業で足りることを記す。
4. The プロジェクト文書 shall 「記事をサブフォルダに置かない(ビルドが止まる)」という、改めた決まりの記述を残さない。
5. The プロジェクト文書 shall 文書(`doc`)の URL には題材のフォルダが入り、記事とは決まりが違うことが読み取れる記述を保つ。
