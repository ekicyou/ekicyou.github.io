# Requirements Document

## Introduction

サイト「えちょのざんがい」(`https://ekicyou.github.io/`)の原稿は、いまリポジトリのルートにそのまま置かれている。開発用の文書を足すたびに公開物への混入を気にする必要があり、ビルドが通るかどうかは `master` へマージして初めて分かる。

この spec は、見た目と公開済みの URL を変えずに、次の 2 つを行う。

- 原稿一式を `site/` の下へ 1 階層下げ、ルートを開発用のファイルだけにする。
- ビルドと公開を GitHub Pages の旧来方式から GitHub Actions に切り替え、PR の上でビルドを確かめられるようにする。

背景と下調べは同じフォルダの `brief.md` にある。全体の進め方は `.kiro/steering/roadmap.md` にある。

この要件はクイック生成(`/kiro-spec-quick --auto`)で作った。要件の話し合いで確かめるはずだった 1 点は、起票時の推奨どおりに置いている(2026-10-11 に開発者へ提示済み。異論があれば 4.3 を直す)。

- ルートの `README.md` は `site/` へ移さない。いまは `/README.md` として公開されているが、公開から外れてよいものとする(中身は題名の 2 行だけ)。

この文書で使う言葉:

- **原稿**: サイトを作る元になるファイル(記事、文書、画像、レイアウトと部品、単独のページ、サイト設定)。
- **開発用のファイル**: 公開しないファイル(`CLAUDE.md`、`README.md`、`.kiro/`、`.claude/`、`.github/`、リポジトリの設定ファイル)。
- **公開パイプライン**: 原稿からサイトをビルドし、公開するまでの自動の仕組み。
- **移行作業**: この spec の実装として行う、移動・切り替え・確かめの一連の作業。
- **公開方式の設定**: GitHub Pages が「何を元に公開するか」を決めるリポジトリの設定。

## Boundary Context

- **In scope**:
  - 原稿の `site/` への移動と、置き場に依存する設定の直し
  - `master` への push で自動的にビルドして公開する仕組み
  - PR の上でビルドだけを行い、成否を示す仕組み
  - 公開方式の設定の切り替えと、その段取り・戻し方
  - 切り替えの前後で公開物が同じであることの確かめ
  - 働いていない古い CI 設定の削除、ビルドに使う部品の版上げを提案する仕組み
  - steering・`CLAUDE.md`・`README.md` を新しい配置と方式に合わせる直し
- **Out of scope**:
  - 見た目・レイアウト・スタイルの変更
  - テーマ指定の食い違いの解消、Jekyll の版上げ、生成ツールの乗り換え(`site-astro-redesign` が持つ)
  - 手元でサイトをビルドする環境づくり
  - ブランチ保護の導入、独自ドメイン、公開先の移転
  - 記事の内容の書き換え
- **Adjacent expectations**:
  - 記事を書く運用は変わらない。開発者は今までどおり `master` へ直接 push してよい。変わるのは、記事の置き場が `site/_posts/` になることだけである。
  - 同じ `ekicyou.github.io` の下で公開されている別リポジトリのページ(`/ghost_dev/`、`/nyan-pu-puu/`、`/zzz-pasta/`、`/old/`)には触れない。
  - 次の spec(`site-astro-redesign`)は、`site/` という置き場、Actions による公開、「PR ではビルドだけ」という振り分けを引き継ぎ、ビルドの段だけを差し替える。

## Requirements

### Requirement 1: 原稿を `site/` にまとめる

**Objective:** As a 開発者, I want サイトの原稿が `site/` の下にまとまっていること, so that ルートに開発用のファイルを置いても公開物に混ざる心配をせずに済む

#### Acceptance Criteria

1. The リポジトリ shall サイトの原稿(記事、記事に添える文書、画像、レイアウトと部品、単独のページ、サイト設定)をすべて `site/` の下に置く。
2. The リポジトリ shall ルート直下に、開発用のファイルだけを置く。
3. The 移行作業 shall 原稿のファイルを、内容と改行を変えずに移す(置き場に依存する設定の直しを除く)。
4. The 移行作業 shall 原稿のファイルを、移動の後も移動の前の変更履歴を辿れる形で移す。
5. The 公開パイプライン shall `site/` の外にあるファイルを公開物に含めない。
6. The リポジトリ shall `site/` の中で、移動の前と同じ相対配置(`_posts/`、`doc/`、`img/` など)を保つ。

### Requirement 2: `master` への push で公開する

**Objective:** As a 開発者, I want `master` へ push するだけでサイトが公開されること, so that 今までと同じ手軽さで記事を出せる

#### Acceptance Criteria

1. When `master` へ変更が push されたとき, the 公開パイプライン shall `site/` の原稿からサイトをビルドし、`https://ekicyou.github.io/` に公開する。
2. The 公開パイプライン shall push から公開までの間、開発者の手作業を求めない。
3. If ビルドが失敗したとき, the 公開パイプライン shall 公開を行わず、それまでの公開物をそのまま残す。
4. If ビルドまたは公開が失敗したとき, the 公開パイプライン shall その実行を失敗として記録し、開発者が GitHub 上で失敗した段と記録を確かめられるようにする。
5. When 公開の処理が進んでいる間に次の push が届いたとき, the 公開パイプライン shall 進行中の公開を途中で打ち切らず、最後に push された内容が公開された状態で終える。
6. When 開発者が手動で実行を指示したとき, the 公開パイプライン shall `master` の原稿からサイトをビルドして公開する。
7. The 公開パイプライン shall 開発者の手元にビルド環境(Ruby など)が無くても働く。

### Requirement 3: PR の上でビルドを確かめる

**Objective:** As a 開発者, I want PR を出した時点でビルドが通るかどうか分かること, so that 壊れた変更を `master` へ入れる前に気付ける

#### Acceptance Criteria

1. When `master` 向けの PR が作られた、または更新されたとき, the 公開パイプライン shall その PR の内容でサイトをビルドし、成否を PR の上に示す。
2. While PR の内容をビルドしている間, the 公開パイプライン shall 公開を行わない。
3. If PR の内容のビルドが失敗したとき, the 公開パイプライン shall PR の上に失敗として示す。
4. The 公開パイプライン shall PR のビルドによって、`master` の公開の処理を待たせず、取り消さない。
5. When PR のビルドが成功したとき, the 公開パイプライン shall ビルドした成果物を、開発者が取り出して中身を確かめられる形で残す。

### Requirement 4: 公開物を変えない

**Objective:** As a 読者, I want 公開済みのページが今までと同じ URL と中身で読めること, so that 古いリンクやブックマークが切れない

#### Acceptance Criteria

1. The 公開サイト shall 切り替えの前に公開されていたパスを、切り替えの後も同じパスで公開する(4.3 の意図した差を除く)。
2. The 公開サイト shall 各パスの中身を、切り替えの前と同じにする(ビルドの時刻など、ビルドのたびに変わる値を除く)。コメント欄の表示、フィード、SNS 向けの情報に含まれる絶対 URL を含む。
3. The 公開サイト shall `/README.md` を公開しない(意図した差。切り替えの前はルートの `README.md` がそのまま公開されていた)。
4. The 公開サイト shall 切り替えの前に公開されていなかったパスを新たに公開しない。`/site/` で始まるパスと、開発用のファイルを含む。
5. The 公開サイト shall 切り替えの前に非公開だった記事(`published: false`)を、切り替えの後も公開しない。
6. When `site/` への移動を `master` へマージする前, the 移行作業 shall 切り替え前の公開物と新しいビルドの成果物を、パスの一覧と中身の両方で突き合わせ、差の一覧を開発者に示す。
7. If 突き合わせで意図しない差が見つかったとき, the 移行作業 shall マージを行わず、差を解消するか、開発者の判断を仰ぐ。
8. When 切り替えの後の最初の公開が終わったとき, the 移行作業 shall 公開中のサイトで、トップページ・記事・文書・画像・フィードの代表的なパスが応答することを確かめ、結果を開発者に報告する。

### Requirement 5: 安全に切り替える

**Objective:** As a 開発者, I want 公開方式の切り替えが決まった順番と許しのもとで行われること, so that 切り替えの途中でサイトが崩れたり、勝手に公開の設定が変わったりしない

#### Acceptance Criteria

1. The 移行作業 shall 公開方式の設定の切り替えを、`site/` への移動が `master` に入る前に済ませる。
2. When 公開方式の設定を切り替える前, the 移行作業 shall 開発者の明示の許しを得る。
3. When `site/` への移動を `master` へマージする前, the 移行作業 shall 開発者の明示の許しを得る。
4. When 公開方式の設定を切り替えた直後, the 移行作業 shall 公開中のサイトが引き続き応答することを確かめる。
5. If 切り替えの途中または後で公開中のサイトが崩れたとき, the 移行作業 shall その場で開発者に報告し、戻し方を示す。
6. The 移行作業 shall 切り替え前の状態へ戻す手順を、切り替えの前に文書にしておく。

### Requirement 6: 遺物を片付け、版上げを提案させる

**Objective:** As a 開発者, I want 古い設定が片付き、ビルドに使う部品の版上げが自動で提案されること, so that 長く放置しても、何が働いているのか分かり、古びた部品に気付ける

#### Acceptance Criteria

1. The リポジトリ shall 働いていない古い CI の設定(`.travis.yml`)を持たない。
2. The 公開パイプライン shall ビルドと公開に使う外部の部品を、版を指定して使う。
3. When ビルドと公開に使う外部の部品に新しい版が出たとき, the リポジトリ shall その版上げを PR として開発者に提案する。
4. The リポジトリ shall 版上げの提案を、開発者の判断なしに `master` へ取り込まない。

### Requirement 7: 文書を新しい姿に合わせる

**Objective:** As a 開発者(と、手伝う Claude のセッション), I want steering と案内の文書が新しい配置と方式を正しく書いていること, so that 次の作業が古い前提で進められない

#### Acceptance Criteria

1. The プロジェクト文書 shall 原稿の置き場が `site/` であることと、ビルドと公開の方式を、切り替え後の姿どおりに記す(`.kiro/steering/tech.md`、`.kiro/steering/structure.md`、`CLAUDE.md`、`README.md`)。
2. The 検証の手順(`.kiro/steering/workflow.md` の「検証」節) shall マージの前の確かめを「PR の上のビルドが成功していること」とする。
3. The 検証の手順 shall マージの後に公開の成否を確かめる方法を、切り替え後の方式で実際に使える手順として記す。
4. The プロジェクト文書 shall 旧来方式を前提にした記述(ルートが原稿である、PR の上では確かめられない、など)を残さない。
5. The プロジェクト文書 shall 切り替え前の状態へ戻す手順を記す。
