## 要約

設計は、今の姿(`site/`、1 ファイル・2 ジョブのワークフロー、公式アクションだけの組み方)にきれいに乗っており、要件の 10 個・受け入れ基準の 100 個すべてに行き先がある。要になる主張(28 個のパス、front matter の定義、数式のスタイルシートの入れ方)は、実物で確かめられた。一方で、実物と突き合わせると、設計の記述と食い違う点が 2 つ見つかった(本文のメールアドレス、基準にする成果物の期限)。どちらも `design.md` の書き足しで直せる大きさで、作り直しは要らない。

## 重大な論点

### 論点 1: 本文のメールアドレスが `mailto:` のリンクになり、成果物の検査が今の原稿で落ちる

- **懸念**: 文書 `entanglement_cosmogenesis_v1_ja.md` の 18 行(「連絡：」の行)に、作者のメールアドレスが地の文で書かれている。今のサイトは文字のまま出している。新しい処理系は、GFM の自動リンクで `<a href="mailto:…">` にする(`design-check` のビルドで確かめた。v1 のページに 1 つ出る)。DistVerifier は「どの HTML にも `mailto:` が無い」を誤りにするので、今の原稿のままでは `npm run verify` が落ち、公開できない。あわせて、SiteConsts の節の「`site/` からもメールアドレスが消える」と、Security Considerations の「ページにも置かない」は、事実と違う。アドレスは、この文書の本文と、そのまま置く TeX(31 行)と PDF に残る。
- **影響**: 実装が検査で止まり、その場で「検査を緩める」か「原稿から消す」かを選ぶことになる。どちらも、3.25 の読み方(枠の話か、ページ全体か)と、本文を書き換えない決まり(2.2、2.15)にかかわり、実装の中で決めてよい話ではない。何も手当てしなければ、アドレスは今より拾われやすくなる(文字 → リンク)。3.25 の理由(迷惑メールの収集)と逆を向く。
- **提案**: 設計ディスカッションで、開発者が次から選ぶ。
  - 案 A: 本文は残し、自動リンクだけを止める。`mailto:` のリンクを文字へ戻す小さな rehype の部品を足し、今と同じ「文字のまま」にする(`remark-gfm` に、メールの自動リンクだけを止める設定は無い見込み。確かめが要る)。検査は今の決まりのままで通る。原稿は直さない。
  - 案 B: 文書から連絡先の行を消す。本文の書き換えなので、「原稿を直す範囲」に 1 種類を足す(要件の直し)。
  - 案 C: 本文のリンクは認め、検査をサイトの枠(ヘッダーとフッター)に限る。
  - どれを選んでも、上の 2 か所の記述を事実に合わせる。TeX と PDF は、1.3 により中身を変えないことを書き添える。検査は、文字の `mailto:` ではなく `href="mailto:` を見る(記事のコードの例に `mailto:` と書いただけで、公開が止まるのを避ける)。
- **対応する要件**: 3.25、2.2、2.15、1.3
- **設計の該当箇所**: 「DistVerifier」の検査の表、「SiteConsts」、「Security Considerations」の「個人の情報」、「Error Categories and Responses」

### 論点 2: 選んだ画面の案を、実装へ渡す経路が決まっていない

- **懸念**: 画面の案は scratchpad(セッションごとの一時の置き場)に作り、決まった後にリポジトリへ入るのは「決まった値」だけである(表に書き込む)。しかし、開発者が画面で見て選ぶのは、値だけではない。`base.css`・`prose.css`・部品のスタイルが作る全体(余白、見出しの飾り、一覧と顔の組み方、目次の置き方)である。表の 13 行は、色・書体・角丸などの値と選択しか受け止めない。`research.md` の §9 は「試作のファイルを写さず、文書から起こす」と言い、`design.md` は画面の案を「試作と同じ扱い」としている。実装が、選ばれた案のスタイルを写してよいのか、起こし直すのかが読み取れない。実装を別のセッションで行うと、scratchpad は手元に無い。
- **影響**: 選んだ見た目と、実装された見た目がずれる。ずれは 9.3(開発者が画面を確かめて許す)で初めて分かり、手戻りになる。「見たうえで決める」(3.13)が、値の一覧だけの話に痩せる。
- **提案**: 設計ディスカッションで次を決め、`design.md` に書く。
  1. **記録の形**: 選ばれた案のトークンのファイルと設定の中身(テキスト)を、`design.md` の表か、spec フォルダの付録に写す。値だけでなく、トップページ・目次・一覧の組み方の選択も書く。
  2. **実装の出発点**: 選ばれた案のスタイルと部品を、実装の下敷きとして写してよい、と書く(画面の案は、この設計の置き場と部品で組むので、捨てる前提の試作とは性格が違う)。起こし直すなら、9.3 の前に、案と並べて見比べる段を置く。どちらにしても、案を切り替える仕組みはリポジトリに入れない(8.2)。
  3. **選ぶときの物差し**: 「見る条件」に、読みやすさの確かめを足す。本文の文字と背景のコントラスト比(4.5:1 以上)を明暗の両方で測る。コードの地の色が、Shiki の配色とトークン(`--color-code-bg`)のどちらで決まるかを決める(3.7、3.15)。
- **対応する要件**: 3.12、3.13、3.7、3.15、8.2、9.3、9.8
- **設計の該当箇所**: 「画面の案」の「作り方」(置き場、決まった後)と「決まっていること、案を見てから決めること」の表、「Migration Strategy」の A・G・L

### 論点 3: 公開済みの URL を守る確かめに、そのままでは動かない手順と、抜けがある

- **懸念**: 3 つある。
  1. **基準の成果物は 1 日で消える**。`master` の最新の実行(2026-10-11 22:25 UTC)の成果物 `github-pages` は、期限が 2026-10-12 22:25 UTC である(`actions/upload-pages-artifact` の既定の保存期間は 1 日)。Migration Strategy の B は「`master` の最新の実行の成果物を取り出す」としか書いておらず、実装がこの期限の後になると取り出せない。
  2. **成果物の検査そのものを確かめる段が無い**。「検査が働くこと」の確かめは、front matter とファイル名の検査だけを挙げている。DistVerifier が、消えたパス・認めない形のパス・`mailto:` を本当に誤りにするかは、どこでも確かめない。何でも通してしまう検査は、通っている限り気付けない。
  3. **非公開の記事が出ていないことは、移行のときの 1 回しか見ない**。パスの形が記事と同じなので、検査は通る。厳しい front matter の定義で打ち間違いは防げるが、後の直しで絞り込み(`publishedPosts()`)を通らない経路ができても、CI は気付かない。
- **影響**: プロダクトの最優先(公開済みの URL を壊さない、非公開のものを出さない)を「仕組みで守る」という、この設計の一番の狙いが、手順の詰まりと検査の穴で弱まる。1 は、9.1 の突き合わせが、マージの直前に行えなくなる。
- **提案**:
  1. 基準のパスの一覧(53 行のテキスト)を、取れるうちに取り、元のコミットの SHA と一緒に spec フォルダへ置く(`.kiro/` は公開されない)。マージの直前に、`master` の先頭が同じ SHA かを確かめる。動いていたら取り直す。取り直す手(新しい push の実行の成果物を 1 日以内に取る、または `master` の実行をやり直す。やり直しは同じ中身をもう一度公開するので、開発者の許しを得る)も、B に書く。
  2. 「1 回きりの確かめ」に、DistVerifier の確かめを足す(保つパスを 1 行だけ無いパスに替える、`dist/old/` にファイルを置く、HTML に `href="mailto:` を足す。どれも終了コード 1 で止まること)。または、判定の関数を分けて `node --test` に載せる。
  3. 非公開の記事を、ビルドのたびに見る。`verify-dist.mjs` が、原稿の置き場から `published: false` のファイルを拾い、そのパスが `dist/` に無く、`index.html` と `feed.xml` にも出ていないことを誤りとして検査する。または、絞り込みを `astro` に依らない関数に出して、単体テストに載せる。
- **対応する要件**: 9.1、9.2、1.1、1.4、1.5、2.11、3.25
- **設計の該当箇所**: 「Migration Strategy」の B と I、「Testing Strategy」の「ビルドの結果の検査」と「1 回きりの確かめ」、「DistVerifier」

## 画面の案の仕組みと手順について

具体の見た目(配色、背景、書体、画像の飾りなど)が決まっていないことは、3.12・3.13 のとおりであり、欠けとして数えていない。仕組みと手順は、案を作って選ぶところまでは足りている。

- 見た目の違いを CSS の変数(トークン)に載せ、明暗の切り替えと同じ仕組みにしている。案の違いが、ページの HTML に入り込まない。
- 実際の原稿を流し込み、見るページ(6 種類)と見る条件(明暗 × 広い幅・狭い幅)を名指ししている。3.12 の求めと合う。
- 案どうしで変える軸(配色の系統、背景、書体)を最低 3 つと決めており、似た案を 2 つ並べるだけにはならない。
- 案の切り替えは起動のときの環境変数で行い、リポジトリに入れない(8.2、9.8)。
- 足りないのは、選んだ後の渡し方と、選ぶときの物差しである(論点 2)。

## 設計の強み

- **URL を決める場所が 1 つで、守り方が仕組みになっている**。記事の URL は `lib/post-path.ts` だけが決め、ルート・一覧・フィード・前後の記事が同じ値を使う。保つパスの一覧と、認めるパスの形を、ビルドのたびに検査する。「人が突き合わせる」から「ビルドが止める」へ移しており、`product.md` の最優先(残ること)に正面から応えている。
- **決めごとが実物で裏付けられ、退けた案と引き換えが書いてある**。処理系、数式、置き場、ビルドの段のどれも、試作と設計の確かめで動かした結果に基づいている。今回の検証でも、数え直した数がほぼすべて合った。依存と閲覧側のスクリプトを最小にしている点も、steering の「凝った機能より壊れにくさ」に合う。

## 小さな気づき(判定には入れない)

- **Node.js の版上げ(7.3)**: Dependabot が提案できないので手順で補う、という要件との差は、設計が自分で挙げている。設計ディスカッションで、この読み方でよいかを開発者に確かめる(`research.md` の §11.7 の申し送りどおり)。
- **別リポジトリの画像は、手元の表示では出ない**: 本文の画像 6 か所のうち 3 か所(`/nyan-pu-puu/…`、`/ghost_dev/…`)は、このリポジトリに無い。「飾らない画像」の候補にも 2 つ入っている。手元の表示のときだけ公開中のサイトから読む手(開発サーバーの代理の設定)を、リポジトリの設定に入れるか、入れないかを決めて書くとよい。入れないなら、9.3 の確かめで、これらの画像の飾りは見られない。
- **移動と直しを分けたコミットは、`master` には残らない**: この spec は 1 つの PR の squash で入る。2.16(移動として履歴を辿れる)を支えるのは、git の名前変更の検出である。直しは 80 行ほどなので検出される見込みだが、移行の記録に、`git log --follow` で辿れたことを書くとよい。
- **`katex` の版のずれ**: 直に入れる `katex` と、`rehype-katex` が使う `katex` が、版上げでずれると、HTML とスタイルシートが別の版になる。検査は気付かない。`npm ls katex` が 1 つの版だけを返すことを、検査かテストに足す手がある。
