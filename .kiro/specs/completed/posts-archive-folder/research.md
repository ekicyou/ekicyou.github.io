# ギャップ分析: posts-archive-folder

- 実施日: 2026-10-28
- 対象: `requirements.md`(Requirement 1〜6)と、今の `site/` の仕組み
- 調べた版: Astro 7.3.8(`site/package.json` で固定。`node_modules/astro/dist` のソースを直に読んだ)

## 1. 要約

- 変える場所は少ない。URL を決める `parsePostId()`(`site/src/lib/post-path.ts`)、一覧を作る `publishedPosts()`(`site/src/lib/posts.ts`)、公開後の確かめ `verify-dist.mjs`、テスト 1 本、steering の 2 か所。コレクションの読み込み(`**/*.md`)は、今のままでサブフォルダを読む。
- **Astro は、同じ公開パスの重複を止めない。** 既定(`prerenderConflictBehavior: "warn"`)では、警告を出して 2 本目を捨てる。この spec の重複の検査(Requirement 2)は、自前で作る必要がある。
- 重複の検査を `publishedPosts()` の中にじかに書くと、`npm test` から呼べない(`astro:content` に依る)。Requirement 3 の 5 を満たすには、検査を `astro` に依らない純粋な関数として切り出す必要がある。
- `verify-dist.mjs` のファイルの拾い方は、すでに再帰で `/` 始まり。サブフォルダの非公開の記事で誤りになるのは、`parsePostId()` に識別子をまるごと渡しているから。`parsePostId()` を直せば、追従はほぼ要らない。
- 新しく生まれる危険: Windows(大文字・小文字を区別しないファイルシステム)の手元のビルドで、`Foo.md` と `foo.md` を別のフォルダに置くと、成果物のファイルがぶつかる。要件(Requirement 2 の 1)は大文字・小文字の違いを「別の名前」としているので、扱いを決める必要がある。

### 2.3 Astro 7.3.8 のふるまい(ソースで確かめた)

1. **同じ公開パスを `getStaticPaths()` が 2 回返したとき**(`dist/core/build/generate.js` 98〜117 行): 既定の `prerenderConflictBehavior` は `"warn"`(`dist/core/config/schemas/defaults.js` 56 行)。警告を出し、**2 本目を捨てて 1 本目だけを出す**。ビルドは止まらない。`"error"` にすれば `PrerenderRouteConflict` で止まる。`"ignore"` なら何も言わない。
   - つまり、今の仕組みでフォルダを許すだけだと、同じファイル名の公開記事 2 本は「片方だけが黙って公開される」(要件の Objective が防ぎたい事故そのもの)。非公開の記事はそもそも `getStaticPaths()` に入らないので、この仕組みでは見つからない。
2. **glob ローダーで識別子が重複したとき**(`dist/content/loaders/glob.js` 116〜131 行): 同じ `id` を別のファイルが作ると `DuplicateContentEntrySlugError`。これも `prerenderConflictBehavior` に従い、既定では警告して後のファイルで上書きする。誤りの文には、2 つのファイルの場所が入る(3 本以上の重複では、2 本ずつ順に出る)。
   - 今の `keepName` はフォルダを含む識別子を作るので、`archive/2004-…` と `2004-…` は別の識別子になり、この検査には掛からない。
3. **識別子の区切り**: ローダーは `tinyglobby` の結果(`/` 区切り)を渡す。Windows でも `entry` は `archive/2004-05-01-foo.md` の形で、`keepName` の結果も `/` 区切りになる。
4. `prerenderConflictBehavior` は、サイト全体の設定である(記事だけでなく、すべてのルートとコレクションに効く)。今の `astro.config.mjs` には書いていない。

## 4. 実装の選択肢

### 案 A: 今の部品を広げる(識別子はフォルダつきのまま)

- `content.config.ts` は変えない(識別子 = `archive/2004-05-01-foo`)。
- `parsePostId(id)` は、最後の `/` より後ろを読む。誤りの文には `id`(フォルダつき)をそのまま入れる → 1.7 を満たす。
- `post-path.ts` に、`astro` に依らない重複の検査(例: 識別子の並びを受け取り、同じファイル名の組をすべて挙げて Error を投げる関数)を足す。`publishedPosts()` が、`parsePostId()` に通した後でこれを呼ぶ。
- `verify-dist.mjs` は、`parsePostId()` の修正で追従する(コードの変更は無し、か最小)。
- 長所: 変える場所が最小。URL を決める場所が 1 つのまま。重複の検査を `node --test` で確かめられる(3.5)。非公開の記事も数える(2.3)。誤りの文にすべての場所を出せる(2.2)。
- 短所: `post-path.ts` の役割が「URL を決める」から「URL を決め、ぶつからないことを確かめる」に少し広がる。`publishedPosts()` は 4 つのページから呼ばれるので、検査も毎回走る(数百件なので重さは問題にならない)。

### 案 B: 識別子をファイル名だけにし、Astro の重複の検出に任せる

- `generateId` をファイル名だけ(`basename`)を返す形にし、`astro.config.mjs` に `prerenderConflictBehavior: 'error'` を足す。glob ローダーの `DuplicateContentEntrySlugError` で止める。
- `parsePostId()` は `/` を見なくてよくなる(識別子に `/` が来ない)。
- 長所: 自前の重複の検査が要らない。非公開の記事も止まる(ローダーの段で見るため)。
- 短所:
  - 設定はサイト全体に効く(doc・pages・すべてのルートの衝突も誤りになる)。今それで止まる箇所は無い見込みだが、影響の範囲が広がる。
  - 3 本以上の重複で、全員を一度に挙げない(2 本ずつ。2.2 を厳密には満たさない)。
  - `npm test` で確かめられない(3.5 を満たすにはビルドを回すテストが要る。今のテストの作りに無い)。
  - 識別子からフォルダが消えるので、1.7 の「フォルダを含む場所」を出すには `entry.filePath` を誤りの文に足す改修が要る。`verify-dist.mjs` は自前でファイル名を切り出す必要がある。
  - 開発サーバーでの名前の変え方(移動の途中)で、Astro が「名前の変え途中」とみなして見逃す処理がある(glob.js 117〜120 行)。

### 案 C: 組み合わせ

- 案 A の自前の検査を正とし、加えて `prerenderConflictBehavior: 'error'` を安全網として足す(自前の検査をすり抜けた公開パスの衝突も、ビルドで止まる)。
- 長所: 自前の検査に穴があっても、黙って片方だけ公開される事故は起きない。
- 短所: 設定 1 行がサイト全体に効く。要件が求める以上の止め方を足すことになる(手間に見合う得があるかは判断が要る)。

## 5. 新しく生まれる危険と制約

### 5.1 大文字・小文字を区別しないファイルシステム(Windows の手元)

- 今は平らな置き場なので、`Foo.md` と `foo.md` は同じフォルダに置けない(Windows では同じファイルになる)。フォルダを許すと、`archive/2004-01-01-Foo.md` と `2004-01-01-foo.md` が共存できる。
- 要件 2.1 では、この 2 本は別の名前で、ビルドは止まらない。公開パスは `/2004/01/01/Foo.html` と `/2004/01/01/foo.html` で別である。
- GitHub Actions(Linux)のビルドと GitHub Pages(大文字・小文字を区別する)では問題が無い。
- **Windows の手元の `npm run build` では、成果物の 2 つのファイルが同じファイルになり、片方が黙って上書きされる。** 手元の `npm run verify` は、片方のページが無いことに気付かない見込み(`listFiles()` は 1 つしか拾わない。kept-paths に無ければ誤りにならない)。
- 選択肢: (a) 要件どおり止めない(手元だけの問題として、文書に注意を書く)、(b) 大文字・小文字を無視して同じなら、警告を出す、(c) 止める(要件 2.1・2.4 との整合を見直す必要がある)。今の原稿には該当する組が無い。

### 5.2 履歴と squash マージ

- `git mv` は中身を変えないので、git の名前の変更の検出(類似度 100%)で履歴を辿れる。399 本は既定の `diff.renameLimit` の範囲に収まる。
- 要件 4.6 は「移動を別のコミットにする」が、`workflow.md` の決まりで PR は squash マージされるので、`master` では 1 つのコミットになる。名前の変更は squash のコミットでも検出されるので 4.3 は保てる見込み。ただし、仕組みの変更と移動が 1 つのコミットに混ざる。4.6 の「別のコミット」が PR のブランチの上だけの話でよいか、確かめておくとよい。
- `tech.md` の R3(戻し方)は、squash のコミットを打ち消せば移動も戻るので、矛盾しない。

### 5.3 その他

- `posts/archive/` のフォルダ名と、ページ `/archive.html`(`archive.astro`)は無関係で、URL はぶつからない(フォルダ名は URL に入らない)。ただし、言葉として紛らわしいので、文書で書き分けるとよい。
- 前後の突き合わせ(5.1)は、`verify-dist.mjs --list` の出力を移す前に保存し、移した後に `--baseline` で比べれば足りる。`compareBaseline()` は判断を人に任せる(終了コード 0)ので、「増減が 0」を判断する手順を移動作業に書く必要がある。
- 公開パスの一覧だけでは、ページの中身(前後の記事のリンク、一覧の並び)の同一は確かめられない(5.3)。ビルドの成果物の HTML と `feed.xml` を、前後でファイルごとに比べる方法がある(`_astro/` のハッシュ名が変わらなければ、ほぼ同じ中身になる見込み。Research Needed)。

## 6. 手間と危険の見積もり

- **手間: S(1〜3 日)** — 変えるのは関数 2 つ、テスト 1 本、文書 2 か所と、`git mv` 1 回。新しい依存も新しい仕組みも無い。
- **危険: Low〜Medium** — 仕組みの変更は小さく、既存の型どおり。ただし 399 本を動かすので、公開パスの突き合わせを誤ると公開済みの URL を壊す(`master` へのマージがそのまま公開)。突き合わせの道具は既にあるので、手順を守れば Low。

## 7. 設計への申し送り

### 判断が要ること

1. 識別子をフォルダつきのまま(案 A)にするか、ファイル名だけ(案 B)にするか。
2. 重複の検査を自前で作るか、Astro の `prerenderConflictBehavior: 'error'` に任せるか、両方か(案 A / B / C)。
3. 重複の検査の置き場所(`post-path.ts` の純粋な関数を `publishedPosts()` から呼ぶ形が、`npm test` で確かめられる唯一の候補)。
4. ~~大文字・小文字だけが違うファイル名の扱い(止めない / 警告 / 止める)。~~ 要件の相談で決着(2026-10-28): 大文字・小文字を区別せずに比べ、同じなら止める(要件 2.1)。
5. 移動の前後の確かめで、公開パスの一覧のほかに、ページの中身(一覧・フィード・前後の記事)まで比べるか(要件 5.3 の確かめ方)。
6. 要件 4.6 の「別のコミット」は、squash マージの後に `master` で 1 つになることを許すか。
7. `verify-dist.mjs` に、重複の検査も持たせるか(ビルドを経ずに確かめられるが、二重になる)。

### Research Needed

- 移す前と後で、`dist/` の HTML と `feed.xml` が文字の単位で同じになるか(`_astro/` のハッシュ名、`entry.id` に依る出力が無いか)。案 A では `entry.id` が変わるので、ページの中に `entry.id` が出ていないことを確かめる(今のコードでは `adjacentPosts()` の比較にしか使っていない)。

### 8.3 synthesis

- 一般化: 「URL はファイル名だけで決まる」と「ファイル名は一意」は、同じ「ファイル名 = 記事の鍵」の 2 面である。両方を `post-path.ts` に置き、ファイル名の切り出し方(最後の `/` より後ろ)を揃える。
- 作るか採るか: Astro の重複の検出(`prerenderConflictBehavior: 'error'`、glob ローダーの `DuplicateContentEntrySlugError`)は、非公開の記事を見ない・3 本以上を一度に挙げない・`npm test` で確かめられない・大文字小文字を同じとみなさない、のどれかで要件に合わない。自前の関数 1 つ(十数行)で作る。
- 簡単にする: `verify-dist.mjs` の変更、新しいスクリプト、比べるための道具、設定の追加は、どれも要らない。基準の作り方は、既存の `--list`・`--baseline` と `git diff --no-index` で足りる。

### 8.4 危険と手当て

- 399 本の移動で公開パスを壊す → 仕組みを変える前のコミットで基準を作り、仕組みの変更の後と、移動の後の 2 回、パスの一覧と `dist/` の中身を突き合わせる。
- `toLowerCase()` は ASCII の外で Windows の扱いと完全には一致しない → 今の原稿の名前は ASCII だけ。実装に `shortcut:` のコメントで残す。
- `publishedPosts()` は `astro:content` に依るので、「非公開も数える」(要件 2.3)は単体テストに掛からない → 呼ぶ所が 1 行で、絞り込む前の `entries` を渡すことを、レビューで確かめる。
